# 地震理赔办理平台

地震后的报案人需要及时收到已认可损失对应的赔款，并能查清争议项目与未到账款项的办理进度。
本平台供 **报案人 / 查勘员 / 理算员 / 付款复核员** 共同使用，把**分项损失核实 → 争议补证与报价 →
逐批接受和解 → 实际付款与回执查询 → 人工更正**连成一条可审计的业务链。

技术栈：**Vue 3 + Vite（前端）、FastAPI + SQLAlchemy（后端）、PostgreSQL（数据库）**，
内置虚构保单与**支付模拟器**，不依赖任何真实保险或银行接口。

---

## 一、核心业务规则（系统行为，而非静态说明）

1. **事件级合同核算**：一次地震事故共享一次免赔额与一个赔偿上限，建筑与室内财产分项查勘但不逐项重复扣免赔。
   - 累计应赔额 = `max(0, 认可损失总额 − 事故免赔额)`，再与事故上限取小；
   - 某批可付额 = 累计应赔额 − 本事故**已成功支付** − **已锁定/在途（结果未知）付款占用**。
2. **两条和解路径履行同一份合同责任**：
   - **部分和解（partial）**：无争议项目先成批，报案人早拿首款；争议项目后续认可后再建补差批次；
   - **整案和解（whole_case）**：所有分项了结后一次成批，接受与付款轮次少，但争议项会拖住全部款项。
   - 整案和解在存在未了结项目时被后端拒绝；部分批次只能纳入已认可项目。
3. **报价绑定项目与材料修订快照**：报价记录 `snapshot_revision`；接受期间认可金额一旦变化（修订号推进），
   接受动作返回**可见冲突**（409 + 冲突明细），报价置为 `conflicted` 失效，须基于最新结论重新报价。
   和解批次接受时做同样的快照冲突检测，冲突即作废并要求重建。
4. **付款纪律**：
   - 付款发起时对报案行加 `FOR UPDATE` 行锁并做在途幂等检查，**两名复核员同时付款只有一笔成功**；
   - **支付超时 / 成功回执丢失 ≠ 失败**：付款保留为“结果未知”并继续占用事故额度，只能凭原网关交易号
     查询回执，**禁止重新生成另一笔付款**；
   - 网关**明确拒绝**不占额度，可在同批次重新发起，原拒绝记录保留审计；
   - 支付模拟器支持四种模式：即时成功、成功但响应丢失、稍后查询成功（第二次查询才成功）、明确拒绝。
5. **历史付款不可静默修改**：已付款项目再发现错误，查勘/理算接口直接拒绝修改，只能建立**人工更正案件**，
   由付款复核员登记处理结论；历史 Payment 与事件轨迹原样保留。
6. **报案详情五类办理状态**，每类均给出阻塞原因与可继续动作：
   `待补证 awaiting_evidence`、`待接受 awaiting_acceptance`、`待付款 awaiting_payment`、
   `支付结果未知 payment_unknown`、`已完成 completed`（另有查勘中/部分履行中的过渡态）。

### 演示案例数据

保单 `POL-EQ-2026-0088`：事故免赔额 **5000 元**、事故赔偿上限 **40000 元**、收款人张报案。
地震报案 `CLM-2026-1120-01` 下三个分项：

| # | 项目 | 报案金额 | 初始结论 |
|---|---|---:|---|
| 1 | 建筑主体墙体裂缝修复 | 20000 | 认可 **18000** |
| 2 | 室内家具与电器损失 | 15000 | 认可 **12000** |
| 3 | 室内吊顶与墙面装修损失 | 10000 | **争议 8000**（待补证） |

- 第三项两天后补证获认可 8000 时：
  - **分批办理**：先付 `18000+12000−5000 = 25000`，补差再付 `8000`（不重复扣免赔），累计 33000；
  - **整案办理**：稍后一次付 `18000+12000+8000−5000 = 33000`。
- 第三项始终未认可：只能先付 25000，整案和解持续被阻塞，剩余责任为 0。

## 五、页面与验证方式

登录后进入报案 `CLM-2026-1120-01` 详情页，页面包含：保单与合同核算卡片（认可总额、累计应赔、
已成功支付、在途占用、剩余责任、免赔/上限）、当前办理状态横幅（阻塞原因 + 可继续动作）、

各角色登录后仅出现其权限内的操作按钮，越权调用后端返回 403。

### 手工验证路径（建议按序）

1. **分批路径 25000 + 8000**：理算员用项目 1、2 建 partial 批次 → 报案人接受 → 赵复核选“即时成功”支付 25000
   → 理算员对项目 3 发起补证 → 报案人补交 → 查勘员认可 8000 → 理算员审核通过 → 再建项目 3 的补差批次
   → 接受并支付 8000，核对累计 33000、剩余责任 0、项目归属两个批次。
2. **整案路径 33000**：重置数据后先完成项目 3 的补证认可，再建 whole_case 批次，一次支付 33000。
3. **第三项不认可**：不处理争议项，整案和解按钮/接口被拒（409），仅 25000 可付，状态显示阻塞原因。
4. **接受旧报价冲突**：理算员对项目 3 报价 → 查勘员改变认可金额（修订号推进）→ 报案人接受，
   页面弹出可见冲突，报价标记“冲突失效”。
5. **两名复核员同时付款**：对同一已接受批次并发调用支付接口，仅一笔成功，另一笔 409。
6. **成功回执丢失**：支付时选“成功但响应丢失”，付款进入“支付结果未知”并占额度、禁止重复发起；
   点击“查询网关回执”后同笔付款转为成功。选“提交超时”则第一次查询仍处理中、第二次查询成功。
7. **人工更正**：付款成功后查勘员尝试修改项目被拒（提示走更正），建立人工更正案件并由复核员处理，
   历史付款金额与状态保持不变。

## 六、实测验证结论（本机实际执行）

执行环境：容器预装 Python 3.12.10 / Node 22.14.0 / PostgreSQL 18.1（127.0.0.1:5432，ccdev）。

1. **自动化测试（真实 PostgreSQL，非模拟）**：`cd backend && .venv/bin/python -m pytest tests/ -q`
   结果 **15 passed**，覆盖两条和解路径、争议不认可、报价/批次冲突、人工更正、角色权限、
   回执丢失、迟查询、拒绝重付、双复核员并发、在途占用防超额、上限截断。
2. **真实 HTTP 端到端核对（uvicorn 运行中，38 项断言全部通过）**：
   - 分批路径：首批实付 **25000.00**，第三项补证认可后补差实付 **8000.00**，累计 **33000.00**、
     剩余责任 **0.00**、状态 `completed`、项目分属两个批次（{1,2} 与 {3}）；
   - 整案路径：争议未了结时建整案批次返回 409，了结后一次实付 **33000.00**，全程仅 1 笔成功付款；
   - 接受旧报价：认可金额修订后接受返回 409 且响应含冲突明细，报价落库为 `conflicted`；
   - 回执丢失：付款进入 `submitted_unknown` 并占用 25000 额度、详情状态为“支付结果未知”、
     重复发起被 409 拒绝；凭原交易号查询后**同一笔**付款转成功，付款记录始终只有 1 笔；
   - 超时模式：首次查询仍处理中（poll_count=1），第二次查询成功（poll_count=2）；
   - 明确拒绝：不占额度，可重新发起并成功，拒绝记录保留（declined + succeeded 各 1 笔）；
   - 两名复核员并发支付同一批次：HTTP 状态为 200 与 409，仅生成 1 笔 25000 付款；
   - 已付款项目修改被 409 拒绝并提示人工更正；更正案件处理后历史付款金额/状态不变；
   - 越权返回 403、未认证返回 401。
3. **前端联调**：`npm run build` 构建成功（dist 产物 191 KB JS / 4.4 KB CSS）；
   `npm run dev` 启动后首页可访问，`/api` 代理到后端，经代理完成登录并取得令牌。
4. **接口文档**：FastAPI 自带 Swagger UI 可访问（`GET /docs` 返回 200）。
5. 当前容器无 docker 二进制，未在本机实际执行 `docker compose up`；Dockerfile / compose /
   entrypoint 与 nginx 反代配置已按一键启动方式交付，容器入口使用幂等初始化脚本（不破坏既有数据）。
